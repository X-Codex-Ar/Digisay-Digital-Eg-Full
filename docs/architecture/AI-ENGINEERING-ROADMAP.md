# AI engineering roadmap

## Repository audit

The platform has three independently deployed apps: the React public site (`public/`), Angular dashboard (`dashboard/`), and ASP.NET Core API (`backend/`). The API owns authentication, organization authorization, CRM workflows, and SQL Server persistence. Firebase currently provides browser analytics only; Supabase provides optional health checking and private object storage. The `ai-agents/` directory is documentation, not a running agent service. The API exposes a disabled-by-default public FAQ assistant using a server-side OpenAI Responses adapter. The dashboard consumes that same public FAQ endpoint for general DigiSay questions and exposes an admin-only request-triage suggestion endpoint. Triage is organization-scoped, redacts email/phone patterns, rate-limited, output-validated, and advisory only. No OpenAI key is configured, so inference remains unavailable until operators configure the provider. There is no AI job queue/outbox, persisted suggestion, accept/edit/reject audit, or AI-specific database schema.

That means AI must be introduced through a backend-owned feature slice. Browser apps must never hold provider credentials, call a model directly with business records, or become a source of business truth. SQL Server remains authoritative.

## OpenAI capability map and non-duplicated assistant design

Use one server-side OpenAI integration and shared safety/evaluation/telemetry layer. Build different, narrowly scoped Application workflows on top of it: a public FAQ assistant, staff-reviewed CRM triage, and (after the data platform exists) an authenticated artist analytics copilot. They must not share chat context or tools. This avoids separate provider clients while keeping authorization and behavior specific to each workflow.

| OpenAI capability | DigiSay use | Status and boundary |
| --- | --- | --- |
| Text understanding | Interpret a visitor's FAQ question or an authorized staff/artist request | Basic FAQ question handling is implemented behind disabled feature flags; it receives only the current question and retrieved public snippets. It does not imply access to or understanding of private records. |
| Text generation | Explain approved public facts or, later, validated analytics results | The Responses API adapter exists, but no key is configured and no inference is enabled. Artist responses require the missing tenant-scoped data APIs first. |
| Function calling | Request a typed, allowlisted backend read such as `get_top_assets(period, metric)` or `get_platform_breakdown(...)` | Not implemented. Artist analytics may add this later; the API must bind verified user/org/asset permissions and validate dates, metrics, and row limits. Never expose arbitrary SQL, raw database tools, or write functions. |
| Structured Outputs | Return a typed triage suggestion or artist metric summary with provenance | Triage currently asks for JSON and validates the result in .NET; provider-enforced JSON schema output is not configured. Artist metrics remain unimplemented. A valid shape is not authorization or proof of correctness. |
| Embeddings | Convert text into vectors for semantic similarity in a selected corpus | Not implemented. Add only if evaluation shows keyword search is insufficient and a named corpus has owners, ACLs, and deletion/re-index rules. |
| File Search | Retrieve passages from approved documents, such as rights policies | Not implemented. This is document retrieval, not revenue calculation. Choose this hosted path or a DigiSay-controlled embedding/search index for a corpus, never both for the same files. Apply document permissions before retrieval. |
| Image understanding | Suggest metadata for authorized artwork/thumbnails | Not implemented. Later, only for rights-cleared files; never determine ownership or legal infringement from pixels. |
| Moderation | Screen applicable user input and generated output for configured safety categories | Not implemented. Required before public rollout and before staff-generated text is exposed; it does not replace domain validation, grounding, or access checks. |
| Streaming | Show a response progressively | Not implemented. Defer until moderation, schema validation, cancellation, and source verification work safely with partial output. Do not stream unvalidated content or tool arguments. |

For an artist question like “What are my top-performing assets this month, and what should I focus on?”, SQL-backed application queries must calculate the ranking and platform totals from authorized, reconciled records. The LLM may explain those results, point out supported trends, and provide a bounded recommendation. It must not invent missing revenue, mix currencies, infer a rights dispute, or change a campaign. Return the reporting period, currency, metric definition, last-updated timestamp, and source references with every answer. If data is missing or stale, say so and do not answer as though the report is complete.

References: [Responses API](https://developers.openai.com/api/reference/responses/overview), [function calling](https://developers.openai.com/api/docs/guides/function-calling), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [File Search](https://developers.openai.com/api/docs/guides/tools-file-search), [embeddings](https://developers.openai.com/api/docs/guides/embeddings), [image inputs](https://developers.openai.com/api/docs/guides/images-vision?api-mode=responses), [moderation](https://developers.openai.com/api/docs/guides/moderation), [streaming](https://developers.openai.com/api/docs/guides/streaming-responses), and [data controls](https://developers.openai.com/api/docs/guides/your-data).

## Recommended first vertical slice

For a first visible pilot, start with a **read-only public FAQ chatbot** after product and security/privacy approval. Use only a small curated set of public service facts and approved site content; return citations/links and a clear contact-form handoff. Do not give the public bot access to CRM, tenant data, arbitrary web search, or write-capable tools. Keep **staff-reviewed service-request triage** as a separate feature: the current provider-neutral foundation is a start, not a live feature. Confirm whether triage will later cover client service requests, public inquiries, or leads; do not merge these data sets implicitly.

For **CRM triage**, the first product slice should return a small typed result: category, urgency, concise rationale, and confidence/evidence fields. Store the result as a separate, versioned suggestion linked to the source record; never overwrite the source record with raw model output. Before implementation, product and security/privacy owners must agree the minimum persisted fields, retention/deletion period, and access policy. The audit trail must capture the suggestion ID and version, tenant and source-record references, provider/model/prompt versions, creation time, and the acting staff member's accept/edit/reject decision, timestamp, and accepted or edited values. Keep raw prompts, full model responses, and unnecessary personal data out of logs and audit records. A staff member must accept or edit a suggestion before it affects routing or workflow state. A provider outage must leave the existing inquiry/CRM workflow usable.

The persisted review lifecycle is a separate record from the immutable CRM source record. Every generated suggestion, including one still awaiting review or later rejected, has a versioned suggestion record with one of these persisted states: `pending`, `edited`, `accepted`, or `rejected`. Valid transitions are `pending -> edited`, `pending -> accepted`, `pending -> rejected`, `edited -> edited`, `edited -> accepted`, and `edited -> rejected`; `accepted` and `rejected` are terminal. Creating a human edit appends a new version linked to the model-generated version and records the editor. It never replaces the prior version. The accepted values are copied to CRM only after an authorized reviewer accepts the current version. The source record is never mutated by model output alone.

Each version retains only the typed suggestion fields needed for review, its tenant/source-record references, model/provider/prompt identifiers, and creation time. An append-only transition audit stores the prior and new state, suggestion version, reviewer identity, UTC timestamp, and the accepted or edited values; a rejection reason is optional and must not contain unnecessary personal data. Apply the approved retention period to all suggestion versions and transition values. When the source record is deleted, delete its linked suggestion content and audit values as well; keep only a non-identifying deletion tombstone if an approved legal or security requirement requires it. Product and security/privacy owners must set the retention period and any tombstone exception before inference or persistence is enabled. Until then, do not persist suggestions or send business data to an external model.

## Architecture and location

- `ai-agents/`: feature specifications, prompt versions, evaluation fixtures, and operator documentation. No credentials or production customer data belong here.
- `backend/src/DigiSay.Application/Features/AI/`: provider-neutral use cases and contracts; the triage foundation exists on the current feature branch but is not enabled at runtime.
- `backend/src/DigiSay.Infrastructure/AI/`: provider client, configuration, minimization adapter, and secret-backed implementation.
- `backend/src/DigiSay.API/`: provider proxy and authenticated/rate-limited endpoints. Public FAQ endpoints must only retrieve public approved content; tenant identity for protected endpoints must come from verified API context, never a client-supplied organization identifier.
- `public/`: public FAQ chat interface only; it receives the answer/citation contract from the API and never holds provider credentials.
- `dashboard/`: general FAQ assistant and read-only triage suggestion UI. Suggestions are not persisted or accepted/rejected yet. Keep provider SDKs and secrets out of browser bundles.
- SQL Server: persist source records and any accepted suggestion/audit state. Use an outbox and background worker if inference becomes asynchronous; neither exists today.
- Knowledge content: start with versioned, curated FAQs. Add vector/search infrastructure only when corpus size and evaluation show it is needed; every indexed document needs owner, visibility, version, and deletion behavior.

Avoid a standalone AI microservice, multi-agent orchestration, or a multi-provider abstraction until a concrete scale or provider requirement justifies them.

## Mandatory gates before external inference

| Gate | Accountable approver | Evidence required to pass |
| --- | --- | --- |
| Product workflow and scope | Product owner (TBD) | Written workflow, target record type, authorized staff roles, success metric, prohibited AI actions, and agreed persistence fields/status lifecycle |
| Provider and data processing | Security/privacy owner (TBD) | Approved provider terms and deployment region; documented lawful data scope, provider retention/training settings, and a reviewed minimization/redaction plan |
| Tenant, runtime, and operations controls | Backend/security owner (TBD) | Passing cross-tenant/authorization tests; configured rate limits, per-tenant cost ceilings, timeout/failure behavior, and a tested operator kill switch |
| Quality and safety evaluation | AI engineer plus product owner (TBD) | Versioned model/prompt, privacy-reviewed representative evaluation set, recorded results meeting an agreed threshold, and documented known failure modes |
| Persistence, audit, and retention | Product and security/privacy owners (TBD) | Approved data schema and retention/deletion period; audit test evidence for accept/edit/reject actor, time, suggestion version, and final accepted values; proof that raw prompts and unnecessary personal data are not logged |
| Human oversight | Product owner (TBD) | Tested staff review flow that blocks workflow changes, messages, billing effects, or legal/takedown actions until an authorized human accepts or edits the suggestion |

Owners marked TBD are an explicit release blocker: assign named approvers before any external inference is enabled. Keep each gate's evidence with the feature's release record. Tests must cover malformed/untrusted model output, provider timeout/failure, rate and cost limits, and accept/edit/reject behavior as well as tenant isolation.

2. **Service-request triage completion:** continue from the provider-neutral Application foundation; approve taxonomy/provider and minimization; add persistent suggestions/audit, endpoint, staff UI, evaluation, and operational controls; retain human accept/edit/reject.
3. **Artist performance copilot (new; domain-first):** inventory trusted platform/revenue/rights data sources; define artist/catalog/platform asset mappings and reconciled reporting facts in SQL; then expose allowlisted read-only analytics use cases. Use OpenAI Responses function calling to select tools, never to calculate totals or query SQL directly. Return structured answers with evidence/period/currency/freshness; no write tools.
4. **Staff content copilot:** after internal brand/content sources and editorial owners are defined, produce drafts only with source links, claim checks, revision history, and editor approval.
5. **Client/internal knowledge assistant:** only after support/project/campaign data APIs, tenant/resource authorization, document ACLs, and corpus lifecycle exist. Separate public, employee, and tenant-private collections and contexts.
6. **Media and campaign intelligence:** after asset/campaign models, rights/consent, data quality, and measurable baselines exist.
7. **Rights evidence ranking:** last, with legal/security review and investigator-only decisions.

For every feature, implement offline evaluation before a user rollout, set measurable acceptance thresholds before seeing production results, track answer grounding/abstention and human correction, and retain a kill switch. Do not introduce autonomous agents, arbitrary tool use, cross-tenant retrieval, or auto-publishing as part of the chatbot MVP.

## Phase 2 foundation status

The current implementation exposes the public FAQ assistant to both the React public site and Angular dashboard, plus an admin-only organization-scoped service-request triage suggestion workflow. Both use one server-side OpenAI Responses adapter and are unavailable until approved provider settings are configured. Triage output is validated and presented for review; persisting, accepting, editing, rejecting, and auditing suggestions remain future work. The artist analytics copilot is a distinct later dashboard use case and cannot be implemented truthfully until artist/catalog/revenue/platform/rights data is modeled and tenant-scoped analytics queries exist. Keep public and authenticated assistant contexts, tools, permissions, and evaluation sets separate.
