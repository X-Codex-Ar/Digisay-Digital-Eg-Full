# Transactional outbox

The API stores versioned integration events in SQL Server in the same `SaveChanges` transaction as CRM lead and service-request changes. `integration.OutboxMessages` is the durable queue. The current CRM payload contains only organization ID, resource ID, and status; it does not contain contact details or credentials.

The dispatcher implementation claims batches using SQL Server `UPDLOCK`, `READPAST`, `READCOMMITTEDLOCK`, and row locks, assigns a five-minute lease, and publishes through `IIntegrationEventPublisher`. Delivery is at least once: a crash after publication and before acknowledgement can cause redelivery, so every consumer must be idempotent using the event ID. Failed deliveries record only the exception type, retry with exponential backoff from 5 seconds up to one hour, and move to a visible dead-letter state after ten failed attempts. Dead letters require operator review and a controlled replay process; no automatic replay endpoint is exposed.

**Dispatch is intentionally disabled in the application host until a durable, idempotent destination publisher and consumer are configured.** The previous logging-only publisher was not a delivery mechanism: acknowledging its log write marked CRM events processed without handing them to any consumer. The API therefore persists outbox rows but does not claim or acknowledge them. When a real destination is approved, register its `IIntegrationEventPublisher` implementation and the hosted `OutboxDispatcher` together, then add integration tests proving successful durable handoff before marking a row processed. Do not reintroduce a logging-only publisher.

Cross-store integration events must continue to use this SQL outbox; request handlers must not send those events directly. The dispatcher uses a system context limited to outbox rows and never queries tenant-owned records. There is no background job that reads CRM entities today.

The outbox migration is `20261125110000_TransactionalOutboxAndTenantListIndexes`. Its `Down` operation drops the outbox table and permanently loses pending, processed, and dead-letter event history; back up the database and use a reviewed staged rollback before reverting it. See [`database/README.md`](../../database/README.md) for migration order and rollback risks.
