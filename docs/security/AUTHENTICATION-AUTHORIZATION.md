# Authentication and authorization

ASP.NET Core Identity in the API is the single user and role authority. Supabase Auth and Firebase Authentication are not independent identity providers. The API exposes Identity endpoints under `/api/v1/auth` for registration, sign-in, refresh, confirmation, and password recovery; `/api/v1/users/me` requires authentication. Emails are confirmed before password sign-in, failed attempts are locked out, and roles are persisted in SQL Server.

The public React site and Angular dashboard are separate SPA clients, so the current contract uses ASP.NET Core Identity's opaque bearer tokens rather than browser cookies. Access tokens expire after 15 minutes and refresh tokens after 7 days. Browser clients should keep both tokens in memory, send access tokens in the `Authorization` header, use `/api/v1/auth/refresh` to obtain replacement credentials, and clear both tokens on sign-out. These are Identity bearer tokens, not JWTs. The built-in refresh tokens are not server-tracked as single-use sessions; clearing client tokens does not revoke a copied access token before expiry. Server-side session revocation and refresh-token reuse protection remain follow-up security work. Production also needs a persistent, shared Data Protection key ring so refresh tokens survive restarts and work consistently across API instances.

Production confirmation and recovery mail use SMTP configuration supplied through a managed secret store. Development can use SMTP values from User Secrets; without them, links are logged locally. Role-protected API groups must use explicit authorization policies, and no organization-owned business endpoint may ship until #4 verifies membership and tenant scope on the server. Angular route guards are navigation UX only; the API is authoritative.
