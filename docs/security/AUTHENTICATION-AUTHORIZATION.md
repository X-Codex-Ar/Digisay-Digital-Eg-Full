# Authentication and authorization

ASP.NET Core Identity in the API is the single user and role authority. Supabase Auth and Firebase Authentication are not independent identity providers. The API exposes Identity endpoints under `/api/v1/auth` for registration, sign-in, refresh, confirmation, and password recovery; `/api/v1/users/me` requires authentication. Emails are confirmed before password sign-in, failed attempts are locked out, and roles are persisted in SQL Server.

Tenant context is a request-only authority. `VerifiedOrganizationEndpointFilter` performs the membership resolution query using both the selected organization ID and authenticated user ID before setting `IOrganizationContext` once. That membership lookup is the named `MembershipResolutionContext`: it may read organization membership rows before a tenant context exists, and it cannot read CRM data. CRM global filters consume only the verified context. `DesignTimeMigrationContext` has an empty organization scope and therefore reads no tenant-owned CRM rows. `RoleSeedContext` writes fixed Identity roles only; `SuperAdminBootstrapContext` is authenticated, requires the one-time bootstrap secret, and does not bypass organization checks. `OutboxDispatchContext` is limited to integration outbox rows and must not query tenant-owned records. No other privileged/system context or background tenant-data job is registered.

The public React site and Angular dashboard are separate SPA clients, so the current contract uses ASP.NET Core Identity's opaque bearer tokens rather than browser cookies. Access tokens expire after 15 minutes and refresh tokens after 7 days. Browser clients should keep both tokens in memory, send access tokens in the `Authorization` header, use `/api/v1/auth/refresh` to obtain replacement credentials, and clear both tokens on sign-out. These are Identity bearer tokens, not JWTs. Session revocation and refresh-token reuse protection are implemented through Identity security-stamp updates. Revoking one session invalidates other refresh tokens for the same account; already issued access tokens can remain valid until their 15-minute expiry. Production still needs a persistent, shared Data Protection key ring so refresh tokens survive restarts and work consistently across API instances.

Production confirmation and recovery mail use SMTP configuration supplied through a managed secret store. Development can use SMTP values from User Secrets; without them, links are logged locally. The organization foundation stores organizations and active/suspended/invited memberships in SQL Server. `X-Organization-Id` is only a selection hint: the API checks its relationship to the authenticated user in the database before setting `IOrganizationContext`, and returns the same 404 for missing and non-member organizations. CRM lead and service-request endpoints are implemented behind verified membership, and EF global filters scope both entity sets to that context. Client organization records are not implemented. Administrative membership management, invitations, audit, and suspended-account operations remain follow-up work. Angular route guards are navigation UX only; the API is authoritative.
