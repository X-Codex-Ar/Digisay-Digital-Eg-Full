# API conventions

The API uses URL-segment versioning. `GET /api/v1/health` is process liveness, `/health/ready` checks configured database dependencies, and `POST /api/v1/contact-inquiries` validates and persists public contact inquiries. Identity endpoints live under `/api/v1/auth`; `GET /api/v1/users/me` requires a bearer token. Authenticated organization routes create an organization with owner membership (`POST /api/v1/organizations` returns `201 Created` with a `Location` header of `/api/v1/organizations/{id}`), read one organization at `GET /api/v1/organizations/{id}` only for an active member (a missing organization and one the caller cannot access both return 404), list only the caller's organizations, and resolve `/api/v1/organizations/current` only after checking the `X-Organization-Id` selector against active membership. Contact and liveness routes are explicitly anonymous. The contact endpoint returns 201 on persistence, 400 for invalid fields, and 429 when its per-IP rate limit is exceeded. The API uses ProblemDetails for unhandled errors and serves OpenAPI only in Development. Every future tenant-owned endpoint must require authenticated membership and scope each read/write by the verified `IOrganizationContext`; never trust the header alone or return EF entities.

## Private storage objects

`POST /api/v1/storage/objects` uploads a file to private provider storage and records its metadata (id, organization, uploader user id, content type, size, created time) in SQL, then returns `201 Created` with `Location: /api/v1/storage/objects/{id}`. `GET /api/v1/storage/objects/{id}` returns that metadata. `POST /api/v1/storage/objects/{id}/download-link` and `DELETE /api/v1/storage/objects/{id}` look the metadata up first; an unknown id and an id owned by another organization both return 404 without calling the provider. SQL and the provider are separate systems, so these operations are not atomic. If the metadata insert fails after the provider upload, the API makes a best-effort provider delete and an orphaned provider object can remain. Delete removes the provider object first and the metadata only afterwards, so a failed delete leaves the metadata in place and can be retried; a provider 404 counts as already deleted. Objects uploaded before metadata was recorded have no row and return 404 through the API.
